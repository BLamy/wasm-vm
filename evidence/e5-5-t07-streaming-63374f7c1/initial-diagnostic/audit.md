## Bounded improvement opportunity

Concrete opportunity: replace `Response(...).arrayBuffer()` plus `Vec<u8>` binding with an incremental SHA-256 + gzip input path that writes decompressed chunks into **one Wasm-owned full snapshot staging allocation**, then invokes unchanged complete-container/component preflight and in-place commit. This removes the simultaneous 634,769,246-byte JS expanded buffer; with the current compressed buffer retained, the named bound becomes about 1,830.298 MiB, a 404.0 MiB reduction versus the proven binding peak. A fully streamed authenticated compressed reader could reduce further, subject to CacheStorage/WebKit behavior. Merely fusing decision+load avoids duplicate work, not the proven later peak.

Direct streaming into guest RAM can be lower still only with two authenticated passes (or transactional page staging): pass 1 must validate gzip/hash, every TLV, sparse total, CPU/RAM/device semantics and identities without mutation; pass 2 may commit from the same authenticated immutable bytes. Do not stream-commit on first sight. A smaller content-addressed warm image also safely lowers both copies if guest free pages are zeroed before capture and equivalent desktop state is proven; publish a new digest/size, never silently replace this object.

Prerequisite/acceptance: add bounded-chunk/hash/inflater tests and allocation counters; run `cargo test -p wasm-vm-core resume`, desktop restore tests, and `cargo build -p wasm-vm-wasm --target wasm32-unknown-unknown --release`; stream-verify the real artifact’s exact digest/TLV list; corrupt first/middle/final compressed and expanded bytes and prove byte-identical machine refusal; then one bounded software warm restore proving ready + echo.
