P9  NOVEL ATTACK — "idle after a position sent since" is not "its pointer stands on it".
    The guest's kernel (Linux input core, input_handle_abs_event) drops an absolute-axis event
    whose value equals the device's current one; a frame of two unchanged axes delivers
    nothing to the compositor. The tablet's values are untouched by relative motion (another
    device). So: pointer at rest on P; relative mode; the guest's pointer is moved by relative
    motion to G; absolute mode; the next absolute position is P again. The guest handles the
    interrupt, moves nothing, goes idle. The page: a position sent since the restart, the
    guest idle after it -> settled, with the guest's pointer on G, a position it never had.
    The next report of the plane (G - h) is compared with P alone; at rest "last sent - plane"
    = h + (P - G) is the only candidate and is taken.
    Unit (real controller; my guest model = the worker's plus two rules: relative deltas move
      the pointer, an absolute position equal to the tablet's last is not acted on), 64x64
      arrow (1,1), P = (400,640), relative motion (-7,-5):
      predicted settling ends; after one commit and the rest wait the page shows (8,6) for a
      true (1,1), for as long as the pointer rests; one more position and a rest: still (8,6)
      (one miss); dropped on the third move it cannot explain.
    Browser (committed bundle; __pointer.setMode("relative",{requestLock:false}), the mouse
      moved a few CSS px (relative frames), __pointer.setMode("absolute"), the mouse moved back
      to the SAME page point), arrow over the page body, terminal printing in bursts:
      predicted for trials where relative motion moved the kernel's plane by d != 0 (|d| small):
      settling ends within 1 s of the return; the kernel's plane does NOT move for the
      returned position; at the reads 0.6 s and 2 s later the page shows (1,1) - d, more than
      a pixel from (1,1); and after two more even steps and a rest the drawn tip is off the
      sent pixel by d. Control in the same run: the return to a point ONE guest pixel away
      from P -> the plane moves, (1,1) or nothing shown.
      What would make this prediction FAIL: the kernel or the device model not dropping the
      repeated axis values; sway not moving its pointer for relative frames of this device;
      Playwright's moves carrying no movementX/Y. Each is checked in the run (plane read
      from /sys/kernel/debug/dri/0/state before and after each step).
    Reach, to be established and stated either way: whether a user of the Replay desktop can
    get into relative mode at all (#ide-pointer-toggle in the desktop layout), and what else
    leaves the guest's pointer off the tablet's last position (session start: the compositor
    places its pointer itself; the boot overlay lets pointer events through only after the
    desktop marker — so not during a normal boot).
