# E5.5-T03e fresh critic predictions

Recorded before running tests or inspecting worker evidence. Scope is the current browser-side
immutable boot cache and startup reporting diff only. E5.5-T03c's unchanged runtime/GUI bindings
remain incrementally HELD; physical-input responsiveness is neither inferred from pixels nor
re-verified here.

## Predictions

- **P1 — exact integrity on both sources.** For independently generated byte bodies, a network or
  cache response returns only when its streamed byte count equals the descriptor size and its
  SHA-256 equals the descriptor hash. Truncated, oversized, same-length-corrupt, opaque, non-200,
  missing-body, and non-byte streams fail before bytes reach the loader or a cache write occurs.
- **P2 — release/hash independence.** Two descriptors for different release hashes use distinct
  CacheStorage keys. A lookup for the new hash cannot consume the old hash entry even when URL,
  role, and size are identical; no broad cache deletion occurs.
- **P3 — corrupt-cache recovery.** A corrupt exact-key cache entry is rejected, that exact key is
  deleted once, and a network request with cache bypass/reload semantics is verified before the
  exact key is repopulated. If the refetch is also invalid, boot fails and no corrupt replacement is
  stored.
- **P4 — storage failure is non-fatal and honestly reported.** CacheStorage access/open/match/delete/
  put failures do not weaken network verification. Access/open/match/put failure permits a valid
  network boot, emits an unavailable source status, and never claims successful persistence.
- **P5 — source-phase accuracy.** A clean hit reports `reading cache` while consuming cached bytes;
  a miss reports `downloading`; a corrupt hit visibly transitions from cache to network; and cache
  unavailability remains visible in the network phase. Progress callback failures cannot affect
  integrity or boot.
- **P6 — transfer/restore UI accuracy.** Unpacking and guest lifecycle states hide/reset any prior
  determinate transfer bar. Generic serial output appends diagnostics without replacing the active
  download/cache/unpack/restore/wait status.
- **P7 — late lifecycle events.** Once desktop readiness is accepted, later generic progress,
  guest-state, guest-ready, and serial events cannot revive the overlay, stale bar, or waiting timer.
  A new `wvm:guest-booting` event starts a fresh lifecycle and can report progress again. Error and
  halt events remain terminal for their active boot.
- **P8 — bounded wait honesty.** `restored` or `guest-ready` arms at most one current-generation
  15-second wait notice; desktop-ready/error/halt/new-boot cancels it, including already-queued stale
  callbacks. The notice says the guest is still awaited and does not claim interactivity.
- **P9 — real reload request proof.** With browser HTTP caching disabled by the proof server, the
  initial real Omarchy boot requests each of kernel, manifest, delta, and snapshot exactly once;
  reload requests none of those paths and reads four independently verified content-addressed cache
  entries. Local and production captures retain real guest presents and no browser errors.
- **P10 — harness/source sufficiency.** The final report binds its source hashes and evidence to one
  frozen HEAD/dist, fails if required source files or real cache entries are absent, and cannot pass
  merely from emitted phase labels, GUI screenshots, or browser HTTP cache behavior.
- **P11 — boundary and regressions.** Only immutable compressed release objects enter the shared
  cache; no RAM, writable disk/overlay, credentials, or cross-session guest state is persisted. CLI
  guest layout/boot behavior and the built ISA suite remain unchanged/green.
- **P12 — test independence.** A bounded novel adversarial test using independently computed hashes,
  randomized chunk boundaries, stale-key poisoning, throwing storage methods, and late-event orderings
  will agree with P1–P8. Sabotaging either hash comparison or exact-size enforcement will make the
  promoted integrity tests fail.
