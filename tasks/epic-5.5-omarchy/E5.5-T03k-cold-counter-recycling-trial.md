## Boundary

One local-only, explicit-opt-in JIT admission trial. T03j measured real
full-table refusals but its first-seen sample did not identify the hot work
behind them. It does not establish the GUI stall's cause. The critic recommends
one controlled counter-recycling A/B, not another probe or parameter sweep.

When a new physical entry encounters a full cold-counter map, the candidate
recycles only that cold history and begins counting the current entry normally.
Do not clear queued/excluded decisions, queued-hit priorities, discovery FIFO,
compile queue, installed code, decoded blocks, guest memory or architectural
state. Do not bump the code generation. Keep the normal threshold and all
other policies. Record actual selection and bounded reset/discard accounting.

The initial implementation is default off so control and candidate are the
same binary with one explicit boot option different. This is an experiment,
not a permanent legacy-compatibility mode or production default. A useful
result must be promoted separately into a clean default and release proof;
a failed result is not deployed or called a fix.

## Deterministic acceptance

`cargo test -p wasm-vm-core --lib --features trace cold_counter_recycling`

- A finite cold flood at the real default threshold must no longer prevent
  a subsequently recurring block from being nominated at that threshold.
  Disabled behavior and admission-probe accounting remain unchanged.
- Recycling is bounded by the existing counter capacity; it does not reset
  nominated/excluded decisions, exact requests, compile priority or generation.
- Changed code and real invalidation retain the existing stale-install checks.
- Deterministic retired trace and architectural snapshots agree with control
  over varied cold-flood/hot-loop schedules. Nomination counts may differ;
  that intentional difference must not be mistaken for architectural drift.
- Selection is an explicit boot option after restore, before execution, with
  actual state returned in existing JIT statistics and no mutation controller RPC.

## Browser trial contract

Use a local-only input-trial path in the existing actual desktop verifier,
reusing its physical key mapping, focus checks and read-only nonce lookup.
Keep R3 LP1, divider64,
JIT on, decoded cache4096, repack-off cap24, profiling/timing off, and admission
observation off in both arms. Never trigger the candidate arm on saturation.

Run control then candidate in separate fresh Chrome processes/contexts, closing
each before the next. Pin the same built binary and exact R3 pair/base bytes;
the only selected runtime difference is the recycling boolean. Record actual
selection, restore, policies, source identities and screenshots in each arm.

Warm-up is the same condition in both arms, not a manually chosen elapsed delay:
real desktop-ready evidence, mapped Foot and its actual active-window identity,
plus a coherent shipped-snapshot restore. Impose an absolute 300,000 ms startup
deadline from navigation through these checks, including asset restore and
serial-query waits. Do not reset it between stages or wait for table saturation.
The unchanged R3 renderer/image proof is carried forward; this trial makes no
new renderer or image-construction claim and does not add renderer-log probes.

When those conditions are met, immediately use the existing physical typing
sequence, capped at60,000ms with the unchanged40ms key delay and focus checks.
Record typing duration separately. Start the unchanged 120,000 ms
readback deadline after Enter, as the existing verifier does; every queued
read-only lookup must fit its remaining deadline. Record a presentation baseline
before typing and require a fresh real presentation after it. Retain a final
post-input screenshot with a bounded capture allowance (20,000 ms); failure
capture/shutdown has a bounded allowance and must not keep the guest running
indefinitely. This trial ends after input proof rather than performing unrelated
reload, second-tab or renderer experiments.

The only meaningful positive outcome is actual physical-keyboard nonce creation
with independent read-only verification within the unchanged 120-second limit,
plus personally inspected real post-input desktop screenshots. Do not type via
serial, extend the deadline, paint fake output, remove the readiness criterion,
or infer success from more compilation/fewer refusals. Preserve failed arms and
report warm-up time separately from input latency and first-boot readiness.

One control and one candidate, not a tuning sweep. If the candidate fails,
retain the failure and stop this policy trial; choose any next scoped action
from the evidence without assuming permission for Epic 6/GPU architecture work.
