## Boundary

The user explicitly requested repair of repeated downloads and misleading boot
progress before the separately tracked E5.5-T03d guest-input remedy. This slice
changes only the browser's immutable boot-asset loading and startup reporting.
Fresh Omarchy guest RAM/disk sessions remain independent and ephemeral. No guest
state, credentials, or writable overlay belongs in the shared asset cache.

## Acceptance criteria

- Repeated loads reuse the kernel, compressed RAM snapshot, disk delta and
  immutable chunk manifest from a persistent SHA-256-keyed asset cache. Verify
  exact length and SHA-256 on both cache and network reads; corrupt bytes never
  boot. Browser reload reuse must be demonstrated with actual server requests,
  not inferred from a progress bar or HTTP cache heuristics.
- A changed release cannot consume a stale hash entry. Corrupt cached bytes
  cause exact-key eviction and a verified refetch. Storage unavailable/quota
  failure preserves a valid network boot without claiming persistence.
- Startup differentiates download, cached read, unpack/restore and waiting for
  the guest. Generic serial traffic never overwrites these phases or leaves a
  completed download bar masquerading as boot progress. Already-restored pixels
  are not presented as proof of interactive readiness.
- Real initial/reload browser captures preserve the actual graphical desktop;
  CLI guests keep their existing layout/boot path. Run the built ISA suite.
- The deployed production path has the same cache/status behavior. No merge,
  bucket deletion, guest-state persistence, or Epic 6 work is authorized here.
