## Boundary

When the Omarchy guest shell is ready but the compositor readiness probe is
still pending, keep the actual display canvas available for keyboard and
pointer input. Replace the blocking full-screen startup card with a compact
noninteractive status strip; retain the strict `wvm:desktop-ready` event and
the full error/halted overlay for lifecycle failures. This slice changes only
the browser startup interaction gate. It does not claim faster guest execution,
compositor readiness, or a successful application response.

## Deterministic acceptance

- Add a browser regression that dispatches `wvm:guest-ready` while the real IDE
  surface is present and proves the overlay is visible only as a status strip,
  has `pointer-events: none`, and leaves the display canvas as the hit target.
- Prove terminal/error/halted and new-boot transitions restore the blocking
  overlay, while `wvm:desktop-ready` still hides it and reports the existing
  readiness state.
- Run the focused startup/UI tests, formatting, the affected browser build and
  the live demo suite. A fresh physical trial must show a pointer frame and a
  later real canvas presentation after a click/keystroke; it may retain the
  existing measured guest latency. No nonce or screenshot may be synthesized.

## Adversarial verification

A fresh critic checks the computed hit target rather than only the DOM flag,
attacks an error and a late terminal event, and verifies that an overlay click
cannot be mistaken for guest input. It carries the existing physical/visible
negative evidence forward and does not promote the nonblocking gate to a
responsiveness claim.

the resulting shell text, but the startup overlay remains a full-screen

isolates the browser interaction gate so the real canvas can receive pointer
events as soon as `wvm:guest-ready` fires. The strict desktop readiness probe,
guest runtime and physical nonce deadline remain unchanged.
