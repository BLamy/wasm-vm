## Boundary

The user requested a fullscreen Omarchy desktop, with the IDE only for CLI
guests. T03k's actual wire records show desktop mode nevertheless runs the
hidden IDE's `ls -la '/root'` at readiness. That command holds the serialized
console bridge for30 host seconds before the desktop layer query can start.
Both runs also send hundreds of binary agent messages; their exact producer
must be identified from code before claiming that they are unnecessary.

Prevent CLI-only guest-service initialization/work for the actual Omarchy
desktop session, preserving normal CLI guest behavior and the real desktop's
keyboard, pointer, resize, presentation and relevant media bridges. Do not
simply hide more DOM or disable all controller input. Identify the current
session from authoritative app state, not an untrusted visual class alone.
Do not change the renderer, image, clocks, JIT policy or input deadlines.

This is removal of demonstrated unwanted work, not a prior claim that it is
the entire cause of the input stall. No implementation starts before T03k's
fresh verdict closes the active lane.

## Deterministic acceptance

`node --test web/tests/omarchy-desktop-services.test.mjs`

- The real service lifecycle starts no CLI Explorer/file-transfer guest work
  for an Omarchy desktop session, including delayed guest-ready events.
- Desktop keyboard/pointer/resize/presentation entry points remain enabled.
- The same lifecycle for Alpine/BusyBox/container-capable CLI sessions still
  initializes its expected IDE/file-transfer services exactly once per session.
- Guest/session changes dispose or fence stale work without suppressing the
  subsequent eligible CLI session. Cover only transitions supported by the app.

Use source-driven integration tests around the actual lifecycle, not a standalone
predicate never called by the app. Run affected browser tests and the built ISA
smoke. Record one bounded actual R3 Omarchy desktop run with unchanged300-second
startup and120-second physical nonce readback limits; inspect actual screenshots
and wire traffic for the removed calls. A screenshot or fewer background calls
alone cannot establish responsive input. Preserve a failed input observation
and keep the broader T03d usability goal unresolved if necessary.

not only the new fixture. No unrelated native gauntlet for unchanged Rust.

### 2026-09-14 UTC — independent critic — pre-result predictions L1–L8

Read the complete active contract before the implementation submission or actual
post-fix run. These predictions concern the guest-service lifecycle only.
T03k's bounded trial and prior unchanged renderer/image/input evidence carry
forward with their limitations; none establishes a responsive desktop.
This entry is not a preflight approval or final verdict.

- **L1 — authoritative winning session.** `wvmDemo.guestSession()` exposes
  the actual winning request's `{ key, generation }`, reflecting the existing
  single-flight owner/boot claim, not the last requested guest, URL, chip or
  `data-wvm-desktop` class. A conflicting boot request cannot change that
  identity. No-owner and retired states cannot authorize guest service work.
  The real IDE and agent call sites consume this state; testing an unused
  predicate is insufficient. Omarchy remains isolated even if stale UI or
  saved sidebar state suggests CLI, and a winning CLI guest is not suppressed
  just because the original page query suggested Omarchy.
- **L2 — no automatic hidden IDE guest work.** With the winning key Omarchy,
  initial ready handling, duplicate/delayed ready events, restored Docker
  sidebar state and scheduled refreshes issue no Explorer `ls`, catalog,
  container `ps` or CLI-only file-transfer initialization. This must prevent
  requests, not merely hide their DOM or silence their output. Omarchy's
  existing `fileTransfer:false` stays unchanged; it is not a newly fixed cause.
- **L3 — dormant agent means no traffic or retained backlog.** Without an
  explicit supported consumer, Omarchy does not start the Channel: no automatic
  HELLO/reconnect or response traffic is sent via `sendAgentInput`. Unsolicited
  incoming bytes while dormant are discarded, including before controller
  attachment, rather than accumulating for later replay. The existing
  128-chunk page buffer is already bounded; this task changes dormant handling,
  not the protocol or global buffering architecture. Merely constructing an
  unused object is not itself a performance finding.
- **L4 — explicit desktop consumers preserved.** An actual explicit restore
  or existing clipboard operation that needs the agent obtains the current
  controller's live Channel lazily, starts it once, and retains its established
  handshake/error behavior. A caller-supplied restore Channel remains honored
  without unnecessarily starting a second default bridge. Repeated consumers
  share the appropriate current bridge; retained references from a retired
  session cannot start or send into a replacement. Do not require a new
  clipboard feature or alter the separate desktop-terminal product path.
- **L5 — CLI behavior and retirement fencing.** Alpine/BusyBox and
  container-capable CLI sessions retain their existing capability-appropriate
  initialization, once per winning generation rather than once per event.
  Retirement cancels or fences polling, pending completions and agent callbacks;
  it neither reactivates hidden work in Omarchy nor prevents the next supported
  CLI session from initializing. The bounded novel attack will schedule a
  CLI refresh/completion, retire its generation through the supported lifecycle,
  then deliver it late with Omarchy owning the page: no new guest RPC, Channel
  startup or stale result application to the new owner may follow. Already
  dispatched commands are not assumed retroactively cancellable.
- **L6 — real desktop controls remain wired.** Canvas/presentation, physical
  keyboard and pointer, display resize, relevant audio/microphone bridges and
  keyboard-LED reconciliation remain enabled through their existing paths.
  The real layers-query-plus-pixels readiness condition remains intact. Do not
  skip the entire IDE module or treat guest-ready, old pixels, absence of
  background traffic, or a removed overlay as desktop-input acceptance.
  Use affected source-driven lifecycle/control tests, not a new native gauntlet
  or additional expensive guest boots, for preservation claims.
- **L7 — one frozen actual R3 observation.** After tests and source/dist freeze,
  the single post-fix actual built-page run retains R3 LP1, the same kernel/
  pair/base, divider64, JIT and existing non-recycling policy, and the unchanged
  navigation-to-qualified-startup300s and Enter-to-readback120s limits. No
  renderer, admission, image or clock experiment is mixed into it. Actual
  served identities, the winning session and raw Worker traffic must support
  absence of the removed automatic calls; zero console-visible commands alone
  misses quiet RPCs. With no explicit agent consumer exercised by that run,
  predict zero `sendAgentInput` calls rather than interpreting opaque bytes as
  shell commands. Inspect the real final screenshots and retain any failure.
- **L8 — result cannot redefine success.** Predict removal of the demonstrated
  hidden work, not that it necessarily cures the stall. Qualification failure
  at300s means input not tested; qualified physical nonce/readback failure at
  the unchanged120s limit is a bounded input negative. Only real physical
  nonce creation/readback plus fresh presentation and inspected desktop pixels
  supports input acceptance. Fewer RPCs or agent messages alone proves service
  isolation, not responsiveness or a measured speedup against T03k. A failed
  product observation keeps T03d unresolved; it does not authorize a tuning
  sweep, another cold boot, production promotion or Epic6 expansion.

The identified call sites justify this scope: `web/ide.js:2735` automatically
