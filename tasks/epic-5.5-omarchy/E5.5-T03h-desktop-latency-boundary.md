## Acceptance criteria

- Bind the actual runtime, image manifest and restored pair. Distinguish
  existing evidence from the newly recorded session.
- Record physical keyboard input, screenshots and controller counters before
  and after a bounded observation, including host input delivery, virtual
  input queue state, guest instruction/clock progress and frame presentation.
- Collect completed, read-only, PID-bound guest process/thread state outside
  the timed input window where possible. Missing or timed-out observations
  remain explicitly unproven; never infer a crash from an IPC timeout.
- Identify the narrowest boundary supported by the measurements and one
  falsifiable next remedy hypothesis, or identify the precise missing probe.
  No claim of responsiveness follows from a diagnostic result.
- A fresh critic independently checks attribution and evidence sufficiency.
  The eventual remedy must separately pass the unchanged 120-second physical
  nonce/readback test and personally inspected actual GUI screenshots.

## Verification command

Use `tools/verify/omarchy-input-diagnostic.mjs` with the explicit unchanged
R3 pair and chunk directory. Record the exact invocation and command stream
in the evidence result. Any diagnostic-helper change requires focused tests
and a frozen head before its final recording; no runtime rebuild is required
for an unchanged built page. A deterministic receipt checker will bind the
collected result before submission.

## Adversarial verification

Reject serial-written nonces, clock/config changes, input acceptance inferred
from host events alone, guest consumption inferred from an empty host queue,
CPU attribution based only on an unbound PID or interpreted-PC samples,
and missing presentations passed off as a host rendering failure. Carry
forward unchanged HELD cases rather than repeating unrelated gates.
