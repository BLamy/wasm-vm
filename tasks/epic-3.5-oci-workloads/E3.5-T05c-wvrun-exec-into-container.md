## Goal
`wvrun exec [-it] <id|name> <cmd…>` — run a NEW process inside an already-running container's
namespaces (the real "docker exec" primitive): join the container's pid+mount+uts+ipc namespaces,
land in its root filesystem (the overlay merged tree), apply its env, and exec the command with stdio
wired to the caller. This is what makes the Docker tab's "exec inside" real rather than a second
independent boot.

## Context
E3.5-T05b tracks a running container's PID 1 in `/run/wvcontainers/<id>/pid`. `exec` must `setns(2)`
into that pid's namespaces — via util-linux `nsenter --target <pid> --pid --mount --uts --ipc
--root --wd` (already in the audited rootfs), or a tiny setns helper if nsenter's `--root` semantics
prove insufficient for the overlay. The subtlety: joining the MOUNT namespace gives the container's
overlay root, but the exec'd process must ALSO inherit the container's seccomp filter and cgroup for
honest confinement parity (a container-escape via exec would be a real finding). Document precisely
which of {namespaces, seccomp, cgroup} exec inherits vs not (v1 may not re-apply seccomp to the
exec'd process — if so, say so, don't imply it).

## Deliverables
- `wvrun exec [-it] <id|name> <cmd…>` joining the container's pid/mount/uts/ipc ns via nsenter/setns,
  cwd + env from the container config, stdio passthrough (`-it` = interactive tty).
- The exec'd process is genuinely INSIDE: it sees the container's PID namespace (its own `ps` shows
  container pids, not guest pids), the container's root (`/` is the overlay, guest-only files absent),
  and the container hostname.
- Honest confinement note in the script header + task log: what exec inherits (ns/cgroup) and whether
  the seccomp filter is re-applied to the exec'd process (and if not, the follow-up to do so).
- Typed errors: exec into a non-existent / already-exited container fails cleanly (no partial join).

## Acceptance criteria
- [x] Start a detached long-runner (T05b). `wvrun exec <id> sh -c 'echo INEXEC_$((6*7)); hostname;
      ls /'` prints `INEXEC_42`, the CONTAINER hostname (not the guest's), and the container root
      listing — proving the exec landed inside the container's ns + rootfs (echo-proof marker).
- [x] `wvrun exec <id> sh -c 'cat /proc/1/comm'` reports the CONTAINER's PID 1 (the entrypoint),
      confirming the pid-namespace join (guest PID 1 would be the guest init).
- [x] A guest-only file planted OUTSIDE the bundle (e.g. `/root/guest-secret`) is NOT readable from
      inside `wvrun exec` (`cat` fails) — the mount-namespace join gives the container root, not the
      guest fs. (Documents the v1 isolation honestly: root-in-guest, no user-ns.)
- [x] `wvrun exec -it <id> sh` gives an interactive shell whose typed commands run in the container
      and whose exit propagates; exec into an exited/absent container → typed error, no hang.
- [x] The confinement-inheritance claims are stated and each is proven or explicitly deferred (no
      silent overclaim of seccomp re-application if it isn't done).

## Adversarial verification
Escape-hunt from inside `wvrun exec`: attempt to read the backing block device, `nsenter` back to the
guest ns, remount `/`, or reach a sibling container's overlay — any success is a finding to document or
fix. Race: exec into a container that exits mid-join → clean failure, no zombie, no leaked ns handle.
nsenter target-pid reuse (the container died and its pid was recycled) must be guarded (verify the pid
still belongs to THIS container's recorded start, e.g. via start-time/cgroup check) — otherwise exec
could land in an unrelated guest process. Native boot proof under `boot_wvrun.rs`.
