## Goal
Grow `wvrun` from run-to-exit into a minimal container LIFECYCLE manager — the guest-side
substrate a Docker-Desktop-style UI needs: start a container detached, list running/stopped
containers with machine-readable status, capture and stream its logs, and stop/remove it. This
is the ~20% of a container daemon that the UI drives; NOT a full Docker Engine, NO daemon socket,
NO image build.

## Context
E3.5-T03 proved `wvrun <bundle>` runs one container to exit with pid/UTS/mount isolation, overlay
image-immutability, memcg limits, and a seccomp filter. The Docker tab needs more than run-to-exit:
it must show a list of containers, their state, and their logs — so `wvrun` must persist per-container
state and detach. Keep it POSIX-sh + the util-linux primitives already audited (E3.5-T02); state lives
in a tmpfs run-dir, logs in a log-dir; no new guest dependencies. Container ids are short random hex
(derive from `/proc/sys/kernel/random/uuid` or `head -c8 /dev/urandom | od`), NOT sequential (avoids
collisions across reloads).

## Deliverables
- `wvrun run [-d|--detach] [--name NAME] <bundle>` — assigns `<id>`, writes
  `/run/wvcontainers/<id>/{status,pid,bundle,name,started}`, tees the container's stdout+stderr to
  `/var/log/wvcontainers/<id>.log`. `-d` returns the id immediately; foreground stays as today.
- `wvrun ps [-a]` — one JSON object per line (`{"id","name","image","status","started","exit"}`);
  `-a` includes exited containers. Stable, parse-safe output (no free-form text on stdout).
- `wvrun logs [-f] <id|name>` — replays the captured log; `-f` follows until the container exits.
- `wvrun stop <id|name>` (SIGTERM→SIGKILL grace) and `wvrun rm <id|name>` (refuses a running
  container without `-f`; cleans the run-dir, log, cgroup leaf, and any leftover mounts).
- Status transitions recorded honestly: `created → running → exited(code)` (or `stopped`).

## Acceptance criteria
- [ ] `wvrun run -d --name c1 <busybox-bundle>` returns an id; `wvrun ps` lists `c1` as `running`
      with that id; the detached container's computed marker (`echo CONTAINED_$((6*7))`) appears in
      `wvrun logs c1` — proving detach + log capture are REAL (echo-proof marker discipline).
- [ ] A detached long-runner (`sh -c 'i=0; while :; do echo TICK_$i; i=$((i+1)); sleep 1; done'`)
      shows `running` in `ps`, `wvrun logs -f` streams successive `TICK_` lines, `wvrun stop` moves it
      to `exited`/`stopped` within the grace window, and a subsequent `wvrun ps -a` shows the exit.
- [ ] `wvrun rm` on a running container is refused (typed error) without `-f`; after stop, `rm`
      removes the run-dir + log + cgroup leaf (verify the paths are gone, no leaked `/proc/mounts`
      entries, cgroup dir absent).
- [ ] Two concurrent detached containers get distinct ids, distinct logs, and independent stop —
      no cross-talk (each log contains only its own marker).
- [ ] `ps` output is machine-parseable JSON lines (a test parses it; a container name with a space
      does not corrupt a field).

## Adversarial verification
Kill `wvrun run -d` mid-start: no half-written state that `ps` reports as `running` with a dead pid
(status must reconcile to `exited`/`dead` when the pid is gone). Reused/duplicate `--name` → typed
error, not two rows. A container that writes a huge log does not fill the guest (bounded log or a
documented cap). `logs -f` on an already-exited container returns the captured log and exits, does not
hang. Native-run under `boot_wvrun.rs` (real Alpine boot) — no simulated states.
