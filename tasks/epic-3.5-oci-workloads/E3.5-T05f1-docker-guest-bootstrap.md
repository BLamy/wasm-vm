## Goal
Give the Docker tab one honest guest session boundary: boot the container-capable Alpine guest in-tab,
detect the runtime from guest files, and make provider/degraded states explicit before any lifecycle
action is offered.

## Context
T05e3 proves the Alpine bridge and T05c proves the guest lifecycle primitives, but the Docker tab still
needs to own boot readiness and capability gating. This slice does not implement image rows or container
actions. It prevents the public busybox build, a missing provider, or a failed Alpine boot from looking
like a partially working Docker daemon.

## Deliverables
- An in-tab Alpine boot affordance wired to `wvmDemo.bootAlpine()` with real progress and typed failure.
- Runtime gating based on the real `wvmDemo.hasContainerRuntime()` result, with no manifest-only guess.
- Honest no-provider state explaining that live pull requires a relay/tailscale provider and that the
  baked set is available; no fake spinner, layers, or progress.
- Public busybox-only degraded state that leaves the catalog surface usable but disables lifecycle work.

## Acceptance criteria
- [ ] A fresh local Chromium visit to the Docker tab can start the real Alpine boot in-tab; success and
      failure are rendered from the bridge result, and a failed boot exposes a typed error without
      pretending a container runtime is available.
- [ ] Runtime controls are enabled only after the guest probe returns true; the public busybox build
      reports runtime absent and shows an honest degraded banner rather than a broken lifecycle UI.
- [ ] With no network provider configured, Pull renders the baked-set/provider explanation and does not
      emit fabricated download progress or layer state.

## Adversarial verification
Use a fresh Chromium context with busybox assets and a context with Alpine assets. Remove or corrupt the
runtime metadata before probing: the UI must fail closed. Trigger boot failure and reload while the boot
is pending: no stale enabled controls or unhandled console error may remain.
