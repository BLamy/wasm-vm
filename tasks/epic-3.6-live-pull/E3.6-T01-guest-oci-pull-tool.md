## Goal
Put the pull half of the OCI pipeline INSIDE the guest so a container image can be fetched while the
VM is running — not baked at build time. A small static riscv64 tool (`wvpull`) that, given an image
ref, resolves the registry manifest, picks the riscv64 image, downloads + sha256-verifies every blob,
and unpacks a runnable bundle into `/opt/containers/<name>` — the same bundle shape `wvrun` (E3.5-T03)
already runs. This is the missing in-guest counterpart to the native `wasm-vm oci pull`
(crates/cli/src/oci/pull) + `tools/oci-sideload.sh`, which today run only on the HOST.

## Context
Why images are baked today (E3.5-T05d) rather than pulled: (1) there is NO pull tool in the guest —
the registry/auth/verify/unpack code is a native host binary; (2) the default guest boots offline.
This task removes blocker (1). Reuse the already-proven Rust OCI logic where possible: the digest
verify, index→arch-manifest resolution, and whiteout-tar unpack are library code in the workspace —
compile them into a `wvpull` binary targeting `riscv64gc-unknown-linux-musl` (the same static-musl
cross-build path as wvft-agent/wvseccomp, tools/build-*.sh). Registry auth = Docker Hub anonymous
bearer tokens over HTTPS. The tool uses the guest's network stack (whatever provider is active); it
does NOT embed a network policy — offline simply means the connect fails with a typed error. Ship it
into the rootfs at `/usr/local/bin/wvpull` (rootfs-inner.sh) like the other guest helpers.

## Deliverables
- `crates/wvpull` (or a `--bin` in an existing crate) — static riscv64 musl, reusing the workspace OCI
  verify/unpack library code; `tools/build-wvpull.sh` mirroring build-wvseccomp.sh.
- `wvpull <repo>[:tag] [--arch riscv64] [--out /opt/containers/<name>]` — resolve → download →
  digest-verify EVERY blob → unpack → emit the `run.json` + `config/*` bundle `wvrun` consumes;
  idempotent re-pull skips already-verified blobs (a poor-man's cache under `/var/lib/wvpull/blobs`).
- Installed into the Alpine rootfs at `/usr/local/bin/wvpull`; catalog update so a pulled image appears
  in `/opt/containers/index.json` alongside baked ones.
- Typed errors: offline/connect-refused, no-riscv64-manifest, digest-mismatch, disk-full — each a
  clear message + nonzero exit, never a partial/left-behind bundle.

## Acceptance criteria
- [ ] Native (host, exercising the guest binary under the emulator OR a native musl run): `wvpull
      busybox --arch riscv64 --out <tmp>` against a real/mock registry produces a bundle byte-identical
      in shape to `wasm-vm oci unpack` (447 entries, argv=`sh`, entry is riscv64 ELF) — proving the
      in-guest tool matches the native pipeline.
- [ ] A blob served with wrong bytes → digest-mismatch, nonzero exit, no bundle written (reuses the
      verified-read path; adversarial tamper proven).
- [ ] A non-riscv64-only ref (e.g. an amd64-only image) → "no riscv64 manifest" typed error, clean exit.
- [ ] Re-pull of an already-pulled image skips blob downloads (cache hit) and still yields a valid
      bundle.
- [ ] `wvpull` is a static riscv64 musl binary (no dynamic deps), shipped at `/usr/local/bin/wvpull`
      in the rootfs (FILE-MANIFEST accounts for it).

## Adversarial verification
The registry is untrusted: manifest, config, and every layer are sha256-checked before use (the
E3.5-T04a MAJOR — unverified manifest — must NOT regress). Token expiry mid-pull refreshes once
(mirror the sideload fix). A malicious layer with `..`/absolute paths or a symlink escape is rejected
by the unpack `safe_path` (reuse the audited applier). Partial download / truncated blob fails the
hash. Disk-full mid-unpack leaves no half-bundle that `wvrun` would run. Cross-build reproducibility
under SOURCE_DATE_EPOCH like the other guest binaries.
