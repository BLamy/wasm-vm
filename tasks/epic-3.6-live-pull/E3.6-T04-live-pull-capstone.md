> **The pulling capstone (Brett: "I want to also prove the capstone with pulling").** E3.5-T05 proves
> the container loop on PRE-BAKED bundles (always-on, zero-network). This capstone proves the SAME loop
> where the image is fetched from a real registry at runtime over a network provider — the "just pull
> it while it's running" milestone — and then survives a reload from the persisted cache.

## Goal
The full live loop in a clean browser: fresh profile → boot Alpine (chunked, persisted) → **pull** a
real riscv64 image from a registry IN-GUEST over a provider → run it → see logs + exec inside →
`page.reload()` → boot → the image is still there from the persisted cache and re-runs with ZERO
re-pull (no registry fetches). Data written by the container also survives the reload (durability).

## Context
This is E3.5-T05 with the baked bundle replaced by a live pull (E3.6-T01→T03) — the graduation of the
whole OCI-in-browser line. It is gated on a network provider (relay proven first; tailscale as a
recorded second leg) and on E3-T19 provider hardening being stable enough for Docker Hub HTTPS. The
persistence proof reuses the E3-T05 double-boot + request-interception pattern: count registry/layer
fetches on the second boot and assert zero. Performance is interpreter-slow (minutes) — "it pulls, it
runs, it persists" is the milestone, not speed. Fresh-stack discipline (memory: `down -v` before each
live run) applies.

## Acceptance criteria
- [ ] Fresh browser profile: boot Alpine with a provider, `wvpull` a real image (busybox first; a
      heavier image as a stretch), `wvrun` it → the guest-computed marker appears in the Docker tab —
      the image ran was fetched over the network at runtime, nothing baked for it.
- [ ] Logs + exec work on the live-pulled container (`wvrun logs`, `wvrun exec -it` — E3.5-T05b/c) —
      the full Docker-Desktop loop on a pulled image.
- [ ] `page.reload()` → boot → the pulled image is present from the persisted cache and re-runs with
      ZERO registry/layer fetches (interception-proven), same computed output.
- [ ] A container write persists across the reload (durability headline — reuse the E3-T08 honest-FLUSH
      / E3-T05 CoW persistence).
- [ ] Offline reload still runs the cached image (no network needed once pulled) — proving the pull was
      a one-time cost, cached durably.
- [ ] Numbers recorded: first-pull bytes/requests/wall time, cached-run wall time, cache size, and the
      exact provider/infra + fresh-stack steps to reproduce.

## Adversarial verification
The second boot MUST prove zero registry fetches (not "few") — interception counts every request to
the registry host. Clearing the persisted overlay forces a re-pull (proving the cache, not a baked
copy, is what survived). A provider outage on the FIRST boot fails honestly (typed error, no fake
run); on the SECOND boot (cached) it still runs offline. Confirm the ran image is the real pulled one
(entry riscv64 ELF, digest matches the manifest), not a baked fallback silently substituted. Do not
claim a heavier image if only busybox is proven — record each image's status explicitly.
