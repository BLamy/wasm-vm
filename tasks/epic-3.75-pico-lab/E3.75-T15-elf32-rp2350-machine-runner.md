## Goal
Run an RP2350-linked ELF32 directly on a selected Pico machine in the native CLI, WASM harness,
and browser test surface without changing Linux `virt` defaults.

## Context
Direct ELF loading is the shortest bring-up path and remains a debugging escape hatch after UF2
boot exists. Machine selection must be explicit: silently interpreting an ELF32 on `virt` or an
ELF64 on RP2350 would make traces and faults misleading.

## Deliverables
- ELF32 RISC-V parsing with segment bounds, entry validation, zero-fill, overlap, and permission
  checks shared with the existing loader where safe.
- `wasm-vm run --machine rp2350 --elf <path>` and an equivalent WASM constructor/test hook.
- A direct-load Pico SDK UART fixture, canonical trace/state output, browser live test, and
  `make verify-E3.75-T15`.

## Acceptance criteria
- [ ] `make verify-E3.75-T15` runs the pinned ELF32 fixture natively and under wasm32 to the same
  halt reason, trace, UART bytes, and state digest.
- [ ] Wrong class, ISA, endianness, out-of-map segments, overlapping segments, and invalid entry
  points fail before machine state changes.
- [ ] Existing CLI invocations still default to the RV64 `virt` machine and preserve goldens.
- [ ] The browser test surface can select RP2350 and marks direct ELF loading `live` with zero
  console errors.

## Adversarial verification
Mutate every ELF header field, construct segments crossing ROM/SRAM/MMIO and 32-bit wrap, and
attempt cross-machine loads. Compare native/WASM errors byte-for-byte. Any partial load,
machine-profile confusion, or ambient-file dependency refutes.
